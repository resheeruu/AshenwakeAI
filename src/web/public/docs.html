Getting started with AshenAI.

Install the bot, sign in to the dashboard, connect a provider, then tighten who can change what.

Reference · updated 2026

Getting started

Add AshenAI to your Discord server, then open the dashboard. Sign in with a username and password, or link Discord or Google OAuth. The first account you create becomes the owner and is the only role that can grant or revoke staff access.

  • Invite the bot and pick the servers it may manage.
  • Sign in at /login and select a server from the server picker.
  • Enable multi-factor authentication while the account is still new.

Dashboard

Each server has its own section for settings, providers, models, moderation, automation, memory, games, analytics and logs. A read-only session still sees everything that role may see — writes are disabled rather than hidden, so operators can audit without being able to change anything.

Authentication

Sessions are HTTP-only cookies with CSRF protection on every mutation. Owner and admin accounts can add an authenticator app for multi-factor authentication; recovery codes are shown once at enrolment and can be regenerated with your password.

Provider management

Configure AI providers through the wizard: Google Gemini, Groq, OpenRouter, Mistral, Anthropic, OpenAI, and local models. Credentials are stored server-side and never returned to the browser.

  • Providers are health-checked and can be disabled without deleting them.
  • Models are bound per provider and can be marked as the default.
  • Credential rotation happens in the dashboard; old keys are discarded.

Free AI mode

The catalog prefers providers and models legitimately available under free or no-cost access. Free access may be subject to provider quotas and can change without notice.

API

Every dashboard action maps to an authenticated HTTP endpoint under /api. Requests carry a CSRF header, and role checks run on the server before any handler executes. Unknown API paths return JSON errors, never an HTML page.

Deployment

Deploy on Render, Docker, Wispbyte, VPS, or Termux. Host-specific configuration — ports, health checks, and build commands — is documented per host.

Security

SSRF protection via a shared network boundary, credential-first classification, CSRF, session hardening, multi-factor authentication, and audit logging. Content security policy is nonce-based: no inline scripts and no inline styles are served.
